# CUAI development roadmap

`state.json` is the local decision and event record. `../roadmap/engine.py` is the deterministic reducer; `cli.py` supports `dry-run`, `apply`, `reconcile`, and `show`. Intake covers enhancements, new products, data assets, evaluation assets, and model assets. Every candidate has a semantic key, source links, existing owner, rank signals, dated evidence, and preserved decision history. User overrides control Next. One development item may be active per brand. New evidence reranks pending work at a safe checkpoint; active work is not silently preempted.

The public draft deployment evidence pilot is the ranked Next CUAI item; owner acceptance has not been verified. Its [fixture](evidence.json) contains only paraphrased public reporting facts and provenance, with no customer or private data. The original announcement is dated September 4; CUAI reporting is dated September 7. CUInsight’s terms and copyright pages restrict reuse of its site content, and no training or redistribution license is established; deployment and independently measured results are unknown. Source availability conveys no training, redistribution, or vendor-review authority. `verify.py` derives the three evaluation answers from record fields. Review rights, corrections, and current source before any public release. Existing publisher policy retains eight articles per full week, while media and social retain their existing caps and gates.

The outbox renders issue #160 protocol comments with stable event and dedupe keys. It is pending until a read of the issue confirms an exact matching receipt. For an ambiguous write, `reconcile` reads authoritative comment bodies and marks confirmed, pending, or conflict. A conflict needs the existing recovery owner; never replay blindly. The outbox itself does not post. Watney coordinates and the CUAI Operating System and existing owners execute within their policies. The retired standalone CEO receives no schedule. Release needs exact existing approval scope, immutable candidate and QA, publisher/deploy checks, rollback owner and steps, and observed production verification. A goal reset is useful planning input, not an execution approval prerequisite.

Example: `python3 automation/roadmap/cli.py dry-run --brand cuai --state automation/product-roadmap/state.json --events /tmp/roadmap-events.json`. `apply` writes local state atomically. Do not commit a changed state until its evidence and canonical issue/PR status have been checked. No CLI command makes an external write.

Approvals and handoff acceptance cannot be asserted through the CLI. The reducer requires an injected verifier backed by the current authoritative source; tests use explicit fixture verifiers. A release approval must bind item, action class, scope, source version, tested artifact hash and commit, remain active and unexpired, and identify a verified source. QA must pass on the exact candidate. Completion must match the released deployment, commit and artifact. A safe checkpoint with a verified recovery owner permits an active item to be deferred or rejected without losing history. Partial issue reads leave ambiguous outbox entries uncertain.

Release and completion also require a fresh authoritative deployment receipt for the same artifact hash, commit and deployment ID; a preview or self-reported environment field cannot complete the item.

See the [integration contract](../roadmap/INTEGRATION.md) for CUAI or `INTEGRATION.md` for CAI, and the unapplied owner invocation patch. The standalone CLI cannot authenticate connector receipts; an authorized host must supply fresh reads to `orchestrate.run_once`.
