# Roadmap adapter integration boundary

`orchestrate.run_once(state, events, provider)` is a bounded pass for an existing owner. It first obtains a complete fresh issue read, reconciles the local outbox, then reduces candidate events. It performs no remote write, publication, deployment or scheduling. `ReadProvider` declares the three required host reads: complete connected GitHub issue comments, exact deployment identity, and an exact committed checkout for local QA. `integrations.py` validates the connected GitHub response shape, exact issue/author, local test result, and production receipt. The reducer re-reads approval at release so a changed or revoked approval cannot ride a cached registration. Rebuild requires a new version-bound receiving-owner receipt. A recovery receipt must bind event, dedupe key, owner, body hash, prior status and fresh authoritative source.

## Remaining protected-transition integration

The saved-snapshot `host_bridge.py` deliberately accepts only intake, dated evidence and ranking proposals. It rejects overrides, handoffs, QA, approval, release, completion and recovery events because replaying one saved issue response is not a fresh read at each action. Those transitions require the existing owner host to call `orchestrate.run_once` with a live `ReadProvider` that invokes the connected GitHub tool anew for each protected receipt and an exact committed checkout for QA. Release/completion additionally need a connected production deployment read plus independently checked deployed-asset bytes. The current no-write bridge demonstrates prioritization only; merging the draft PRs by itself will not create autonomous delivery.

QA receipts require the artifact path itself to be Git tracked. The runner rejects dirty tracked and unexpected ignored inputs before and after tests, with a narrow allowlist for generated build directories and Python bytecode. Generated assets need a separate provenance verifier before they can be used as QA artifacts.

## Candidate intake and state commit protocol

The owner reviews a JSON array of dated candidate records before passing `--candidates <path>` to the bridge. Each record needs `key`, `kind`, `title`, `source`, `observedAt`, and `finding`; `goalId` and numeric `signals` are optional. The intake builder derives stable event IDs, deduplicates by semantic key and dated source, and preserves newer signals against older evidence. An issue comment read supplies reconciliation context; it does not create candidates. The bridge returns a proposal hash without saving it.

For activation, an authorized host must own an authoritative versioned state store implementing `StateStore.read` and atomic `compare_and_swap`. After fresh reduction, call `persistence.commit` with the revision and hash read before the pass. On a lost write response, it re-reads and recognizes an exact committed proposal; on any other conflict it stops for a fresh reduction. Never post an outbox body solely because state commit succeeded: fetch the complete issue again, compare exact event ID and body hash, and let `reconcile` decide. Ambiguous external effects require an authoritative recovery receipt; no blind retry.

Protected transitions use a host backed by fresh connector calls for *each* receipt via `orchestrate.run_once`, not `SnapshotProvider`. Approval registration and release are separate reads, so a revoked or changed receipt blocks release. The current bridge has no live provider or persistence binding and is planning only. The minimal activation decision is whether to bind the existing authorized owner run to a durable versioned store and fresh connected provider. Existing action-specific gates remain.

`StateStore` is an abstract protocol only. The test fake is in memory; neither repository contains an authoritative connector-backed atomic store binding. The authorized existing owner host must supply a durable state location, an atomic compare-and-swap action for it, and fresh connected read access. Until those are available, state persistence is not integrated and the bridge cannot activate delivery.

## Connected durable binding and one-shot issue dispatch

`github_store.GithubContentsStateStore` binds the existing brand state file to the connected GitHub Contents read/update actions on an exact branch. Its revision is the Git blob SHA required by the Contents update action; `run_bound.run_bound` re-reads, reduces with a live `ReadProvider`, and commits through that compare-and-swap. The owner host must pass successful connector `structuredContent` to its callbacks and must never replace a rejected SHA with the latest value without re-reducing. A draft-branch state is not live operating state. Merge/activation must first establish the exact authorized main-branch owner and current state.

`outbox.dispatch_one` reads the full issue, writes a durable `uncertain` claim before a single issue comment attempt, then re-reads and confirms the exact event/body. A lost post response is reconciled without a second post; if no exact receipt appears, the claim stays uncertain until an authoritative recovery receipt resolves it. This is a host-callable adapter, not an unattended runner. The October 14 proposed handoffs are separate issue-bus requests: CUAI issue #160 comment 6175417087; CAI issue #12 comment 6175423207. Neither is a receiving-owner acceptance or an active development stage.
