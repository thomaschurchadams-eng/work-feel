# Reliability Watch integration boundary

The existing `scripts/run-secure-operations.cjs` executes in an ephemeral GitHub Actions job on `main`. Its run 38257568883 receipt stopped at the three-minute production identity wait for eb075a6 with zero side effects. The later READY deployment is external evidence, but the failed job cannot resume after exit. The repository's local file adapter cannot persist a lease or checkpoint across separate hosted Actions workers.

The existing operations runner now emits a sanitized `recovery` handoff in its uploaded run receipt on failure: original run/SHA incident key, failed stage, pre-invocation action-start state and acknowledgment counters. Zero acknowledgments must never be read as proof of zero external side effects. This is the repository-side integration point. The current `reliability-watch` owner is an externally managed Cloud task, coordinated through issue #160. This repository does not contain that task's executable prompt, state store or issue-writing credentials. Wiring this helper into `run-secure-operations.cjs` would put incident closure under a different actor and would still lose its checkpoint when the job ends. No active task, schedule or production workflow is changed by this PR.

To activate the reviewed behavior within the existing owner, the Reliability Watch task needs a shared transactional checkpoint store with atomic per-incident lease/CAS, exact external `isClosed` lookup and same-key idempotent close for issue #160. The owner should ingest the failed run receipt and exact deployment SHA, reconcile every prior side effect, then invoke `recover` with only the unfinished authorized steps. Map permission denials to `PERMISSION_DENIED`, transport-unknown writes to `AMBIGUOUS_OUTCOME`, and verify exact production and persisted result before close. Keep the original incident key and existing approval boundaries. The file adapter and isolated integration fixtures show the contract; they are not suitable as cross-worker Cloud state.

Activation requires a separately reviewable update to that externally managed task and its durable store. Until then, this draft provides a tested implementation contract and a handoff, not automatic recovery.

## Nonproduction connector probe (October 12)

A dedicated `test/recovery-checkpoint-cas-20261012` branch was used without touching `main` or the draft PR. Two distinct commits attempted to update the same starting ref with the same `expected_sha`. One returned success and the other returned `UNKNOWN` from GitHub GraphQL; a later stale-expected retry also returned `UNKNOWN`. The branch contained only the first candidate after both reads. A later successful update whose response was deliberately ignored was recovered by reading the expected payload from the branch. This proves branch-state readback for a lost response, but **does not prove the connector exposes a reliable atomic conflict result under every race**. The `git-ref-checkpoint-store.cjs` adapter remains disabled by default (`casVerified:false`) until an exact connector binding and conflict tests establish its compare-and-swap semantics. Do not activate it from the enabled Reliability Watch task or treat the probe branch as a production store.

Read-only historical replay: run 38257568883 artifact `11750913885` belongs to eb075a6 and the existing issue #160 completion comment `6125747183` already records the exact READY deployment and zero recorded actions/reconciliations/source retries. The existing key is closed; no comment, rerun or write is appropriate.
